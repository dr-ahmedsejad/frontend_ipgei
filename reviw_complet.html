1. Sécurité

1.1 Findings critiques CRITIQUE

1.1.1 Dump SQL avec hashes pbkdf2 de tous les utilisateurs committé dans git

Fichier : siga/deploy/dump.sql (3063 lignes, commit de8868b du 08-05-2026)

Le dump contient les hashes pbkdf2_sha256 de tous les utilisateurs (admin sejad, IT, étudiants, enseignants) avec username, email, role, NNI étudiants. Ces hashes sont crackables hors-ligne. De plus, plusieurs comptes étudiants/enseignants ont pour mot de passe leur NNI/nbac (cf. finding 1.2.1) — bypass possible si l'attaquant connaît un NNI public.

Action : git filter-repo --path deploy/dump.sql --invert-paths, rotation immédiate des mots de passe admin/IT/DE/scolarité, ajout au .gitignore.

1.1.2 Secrets de production sur disque dans deploy/.env

Fichier : siga/deploy/.env

Le fichier contient SECRET_KEY=a1IchqNNngwYTB9xZXzZBy16tnGOxJNFYU-... et DB_PASSWORD=siga_local_dev_2026. Bien que deploy/.gitignore exclut .env, il faut vérifier qu'aucun commit historique ne le contient et qu'il n'est pas embarqué dans une image Docker poussée.

Action : git log --all --diff-filter=A --name-only | grep deploy/.env ; si trouvé → purge + régénération de SECRET_KEY et DB_PASSWORD.

1.1.3 .env racine du backend committé

Fichier : siga/.env (commit initial a9c44041)

Contient SECRET_KEY=change-me-in-production, DEBUG=True, DB_PASSWORD= (vide). Pas de secret réel exposé aujourd'hui, mais c'est le mauvais pattern : tout commit ultérieur qui injecte un vrai secret le rendra public. Aucun .gitignore racine n'existe.

Action : git rm --cached .env + créer .gitignore racine.

1.2 Findings hauts HAUTE

1.2.1 Mots de passe initiaux devinables (NNI/nbac)

Fichiers : siga/apps/inscriptions/views.py:120 ; apps/absence/views.py:431 ; apps/prof/services.py:149 ; apps/authentication/management/commands/create_student_accounts.py:93

Étudiants → password=nbac (numéro de bac, public). Enseignants → password=NNI (carte d'identité). Le flag doit_changer_mdp=True est posé, mais tout compte non encore consommé est compromissible avec une information publique.

Recommandation : Générer un token aléatoire secrets.token_urlsafe(12) envoyé hors-bande (SMS/email/papier).

1.2.2 RBAC permissive par défaut sur les ViewSets sans required_module

Fichier : siga/core/permissions.py:41-47

RBACPermission ne s'applique que si required_module est défini sur la vue : if not module_code: return True. Tout ViewSet héritant uniquement de IsAuthenticated (default DRF) sans required_module est accessible à n'importe quel utilisateur authentifié.

Recommandation : Auditer chaque ViewSet pour exiger soit required_module, soit une permission_classes explicite. Ajouter un test smoke par module.

1.2.3 38 sérialiseurs utilisent fields = '__all__' (risque mass-assignment)

Exemple critique : siga/apps/authentication/serializers.py:184 — ModuleActionSerializer. Permet une édition non contrôlée via API (création/écriture de champs sensibles comme created_by, is_active, validee_par).

Recommandation : Remplacer fields = '__all__' par whitelist explicite + read_only_fields, au minimum sur les serializers RBAC (Module, Action, ModuleAction, RoleDefault, UserPermission).

1.2.4 CSRF absent sur les endpoints DRF cookie-auth

Fichier : siga/core/authentication.py:11-30 + siga/settings/base.py:60-73

CookieJWTAuthentication identifie via cookie httpOnly, mais DRF bypasse CSRFViewMiddleware quand l'auth n'est pas SessionAuthentication. Le frontend envoie déjà X-CSRFToken mais le backend ne le vérifie pas. Vecteur CSRF en POST cross-origin (cookie SameSite=Lax ne protège pas tous les cas).

Recommandation : Ajouter une vérification CSRF custom dans CookieJWTAuthentication.authenticate, ou passer SameSite=Strict en prod.

1.2.5 Régression CLAUDE.md règle non-négociable n°1 : 13 pages dashboard utilisent encore apiFetch direct

Devait être 0 selon CLAUDE.md. Pages concernées : payement/{liste,ajouter,modifier/[id]}, emplois/gerer, enseignant/{reclamations,suivi}, inscriptions/derogations/ajouter, parametres/semaines/ajouter, profs/{ajouter,[id]}, comptes/ajouter, em/ajouter, suivi/{rattrapage,remplissage}.

1.3 Findings moyens MOYENNE

1.3.1 Endpoint public /preinscriptions/suivi/?numero_dossier=<uuid> (inscriptions/views.py:163) : AllowAny + throttle 20/min anonyme = 28 800/jour pour énumération distribuée. UUID = espace énorme donc risque acceptable, mais resserrer à 5/min.

1.3.2 /institutions/active/ public (apps/parametres/views.py:294) : InstitutionSerializer avec fields='__all__'. Vérifier qu'aucun champ interne (paths absolus, tokens) n'est exposé. Créer un InstitutionPublicSerializer restreint.

1.3.3 DEBUG=True en development.py avec ALLOWED_HOSTS=['*'] + .env racine committé avec DEBUG=True : risque info-leak si bascule prod oubliée.

1.4 Findings faibles FAIBLE

  • Swagger /api/docs/ exposé sans auth (siga/urls.py:17) : restreindre via SERVE_PERMISSIONS = ['rest_framework.permissions.IsAdminUser'].
  • Frontend stocke AuthUser en localStorage (lib/auth.ts:75) : pas de tokens (cookies httpOnly OK), mais identité/rôle exfiltrables via XSS.
  • FileDropzone.tsx n'utilise pas validateUpload central : risque de divergence entre les deux implémentations.
  • Pas de protection ReDoS sur lookup_value_regex (inscriptions/views.py:144) : regex [0-9a-f-]+ non bornée. Resserrer à un UUID strict.
Bonnes pratiques observées : JWT en cookies httpOnly, axes brute-force, throttling DRF, safeNextUrl / safeImageSrc / validateUpload en place côté frontend, pas de dangerouslySetInnerHTML, pas de tokens en localStorage, pas de cursor.execute avec f-string dans le code applicatif, pas de pickle.load / yaml.load, password_hashers Django par défaut.

4. Performance

4.1 Risques N+1 (top 5)

4.1.1 _compute_charge_permanents — IMPACT ÉLEVÉ

apps/avancement/views.py:380-490. Boucle for prof in profs: sur 150-300 enseignants avec, à chaque tour, 3 sous-requêtes (SuiviePointage.objects.filter(prof_id=...), Vacation.objects.filter(prof_id=...), ChargeInstitution.objects.filter(prof=...)). Jusqu'à 900 requêtes par appel. Solution : 3 aggregate groupés values('prof_id').annotate(...). Gain estimé : ÷ 30-50× la latence de l'endpoint.

apps/absence/views.py:562-582. update_or_create dans for item in d['presences']: → 2 requêtes par étudiant. Une classe de 30 étudiants = 60 requêtes. Solution : bulk_update après préchargement, ou INSERT ... ON DUPLICATE KEY UPDATE MySQL natif.

4.1.4 inscriptions/views.py:826 : action elements sans prefetch_related('notes'). Le _notes_map downstream peut repasser en N+1.

4.1.5 20 for ... in Model.objects.all() dans evaluations/views.py — à réviser cas par cas.
